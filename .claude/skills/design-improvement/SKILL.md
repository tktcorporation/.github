# 設計改善 — 初見の読み手が意味を正しく推測できるコードにする

このスキルの判定基準は 1 つで、**コードベースを何も知らない評価者が、そのコードを読んで意味を正しく推測でき、読みにくいと感じないか**である。KISS・SSOT・責務分離・抽象化・命名・ドメイン知識の置き場所は、この基準を満たすための手段として使う。原則に合っていても読み手が誤読するなら改善になっていないし、原則名を挙げられなくても読み手が正しく読めるなら直さない。

## 手順の全体

1. **測る**：予備知識の無い読み手に対象コードを読ませ、誤読と引っかかりを集める
2. **診断する**：集めた誤読ごとに、どの原則が崩れているかを特定する
3. **直す**：原則どうしが衝突する箇所は下の判断基準で決め、意味の単位で直す
4. **測り直す**：別の新しい読み手に改善後のコードを読ませ、推測した意味を意図と突き合わせる
5. **報告する**：直したもの、直せずに残った誤読とその理由を、読み手への影響が大きい順に書く

自分で「読みやすくなった」と判定して終えない。書いた本人は意図を知っているので、名前と中身のずれに気づけない。

## 1. 測る：読み手テスト

新しい文脈のサブエージェントを読み手にする。渡すのは対象のコードファイルだけで、設計メモ・診断結果・会話の経緯・このスキルは渡さない。質問は毎回同じものを使う。

```text
あなたはこのコードベースについて何も知らない評価者です。<対象ファイル> だけを読んでください。
推測で構いませんが、各回答に確信度（高/中/低）を付けてください。
1. このモジュールは何をするものか（2 文）
2. 公開されている各関数・型・定数が何を意味し、どんな場面で使われると思うか
3. 主要な関数を呼ぶと何が起き、どんなときに失敗や空振りになるか
4. 読んでいて引っかかった箇所、意味を推測しきれなかった箇所を、該当行の引用付きで全部挙げる（無理に作らない）
5. 名前とやっていることが食い違っていると感じた箇所
```

この読み手は定義側しか読まないので、呼び出し箇所での読みやすさ（boolean 引数や位置引数の意味）は検出できない。呼び出し側は、実際の呼び出し箇所を読むか、呼び出し 1 行を書いて診断の表で確かめる。

回答を意図と突き合わせ、ずれを次の 3 種類に分ける。

| 種類 | 例 | 扱い |
| --- | --- | --- |
| **誤読**：推測した意味が意図と違う | `estimateTotal` を概算だと読んだが、実際は確定額 | 必ず直す |
| **詰まり**：確信度が低い、または推測しきれない | 「この 50 は 2 つで同じルールか」が分からない | 直す。直せないなら理由を報告する |
| **外部依存**：ファイルの外を見ないと判断できない | `db.query` が 1 行を返すか配列を返すか | このファイルの読みやすさの問題ではない。型や名前で補えるときだけ補う |

数行の関数 1 つを直すだけなど、読み手テストより自分で読む方が早い規模では省略してよい。省略したことは報告に書く。

## 2. 診断する：誤読を原則に対応づける

誤読や詰まりの多くは、次のどれかで説明できる。表の「確かめ方」は、原則に違反しているかを見た目でなく意味で判定するための問いである。

| 原則 | 読み手に起きること | 確かめ方 |
| --- | --- | --- |
| **命名** | 名前から想像した動作と実際の動作が違う。名前から何も想像できない（`process`、`data`、`flag2`、`handle`） | 名前だけを見せて、中身を正しく言い当てられるか |
| **呼び出し側の読みやすさ** | `send(id, true)` の `true` のように、呼び出し箇所だけを見ても引数の意味が分からない | 呼び出し 1 行だけを見せて、何が起きるかを言い当てられるか |
| **SSOT** | 同じルールが複数箇所にあり、どちらが正か、差があるのかを探す羽目になる | 片方の仕様が変わったとき、もう片方も**必ず**同じく変わるか |
| **責務分離** | 1 つの関数やモジュールが無関係な仕事を抱え、どこまでが一続きの話か分からない | そのまとまりが変わる理由を 1 文で言えるか |
| **KISS** | 実装が 1 つしかないインターフェース、引数を取らないファクトリ、中身を素通しするだけのラッパーを、読み手が開いて確かめる羽目になる | その間接層を消すと、読み手が知るべき情報が失われるか |
| **抽象化の水準** | 1 つの関数の中で業務の流れと文字列の組み立てが混ざり、全体の流れが追えない | 関数本体を、同じ水準の手順を並べた文章として読めるか |
| **知識の置き場所** | ルールがコメント・ドキュメント・呼び出し側の条件式にしか無く、コードの構造から読み取れない | そのルールをコードのどこか 1 か所で名指しできるか |

知識の置き場所の観点で、状態を型で表す・ルールを宣言として持つ・モジュールを概念で切るといった具体的な手法が要るときは [references/domain-modeling.md](references/domain-modeling.md) を読む。

## 3. 直す：原則が衝突したときの判断基準

### SSOT と責務分離：式の一致ではなく、変わる理由の一致で統合する

2 か所が同じ式でも、それぞれが表すルールが別なら統合しない。統合すると、片方の仕様変更がもう片方を巻き込み、読み手には「なぜこの判定をここで使うのか」が分からなくなる。

```ts
// 統合しすぎ：確定処理の可否を「発送できるか」で判定している。
// 読み手は、確定と発送がどう関係するのかを推測できない。
if (!canShip(order)) return { ok: false };

// 別のルールとして名前を分ける。今は条件が同じでも、それぞれの理由で変わりうる。
if (!canConfirmTotal(order)) return { ok: false };
```

分けた側には、別にしている理由を 1 文書く。書かないと、同じ中身の関数が 2 つ並んでいる理由を読み手が推測できず、次の改善でまた統合される。

逆に、片方が変わればもう片方も必ず変わる関係なら、見た目が違っていても 1 か所に寄せる。同じルールを、条件式と、優先順位つきの if の並びという別の書き方で持っている場合などが当たる。

偶然同じ値になっている定数も同じ考え方で扱う。ユーザー名と会社名の上限がどちらも 50 文字でも、別々に変わりうるなら定数を分ける。

### KISS と抽象化：読み手が中身を開かずに済むときだけ抽象を置く

抽象（関数・型・モジュールへの切り出し）を置いてよいのは、その名前を読めば中身を開かずに呼び出し側が読めるときである。名前から中身を推測できない抽象は、読み手に中身を開かせるので、置かない方が読みやすい。

- **置く**：名前だけで意味が伝わり、呼び出し側の流れが短く読めるようになる切り出し
- **消す**：実装が 1 つだけのインターフェースとファクトリ、「将来の差し替え用」の拡張点、引数を素通しするだけのラッパー
- **待つ**：似た処理が 2 か所にあるだけで、共通部分にまだ名前が付けられない場合。3 か所目が現れて共通の概念に名前が付くまで重複のままにする

文字列の `type` で無関係な処理を振り分ける汎用関数は、誤った抽象の典型である。呼び出し側からは何が起きるか読めないので、処理ごとの関数に分ける。

### 名前と動作が食い違うとき：名前を直すことを優先する

名前のずれは、読み手が誤読する最も大きな原因になる。公開 API などで名前をすぐ変えられないときも、問題を報告の脇に置かない。

1. 中身に合った名前の関数を作り、旧名は非推奨の別名として残す
2. それもできないなら、残った誤読として報告の先頭に置き、改名の影響範囲を添える

### 挙動を変えない

設計改善では、外から見た挙動（戻り値、副作用、例外）を変えない。改善中に見つけた不具合や仕様の曖昧さは、直さずに報告へ回す。どうしても挙動が変わる変更（引数の形の変更など）は、呼び出し側に必要な修正とあわせて明記する。

## 4. 測り直す

改善後のコードを、1 で使っていない新しい読み手に読ませる。同じ読み手を使い回すと、前の版の記憶で読んでしまう。

- 誤読がゼロになるまで 2〜4 を繰り返す。最後の読み手テストは最後の変更の後に行う。テスト後に足した修正は、小さくても確かめていない変更として残る
- 詰まりは、残っていても理由（外部依存、挙動を変えないと解消できない、など）を説明できればよい
- 改善で新しく生まれた詰まりが無いかを見る。抽象や定数を足した結果、読み手が定義を追いかける回数が増えていたら、その変更は戻す

## 5. 報告する

報告は次の順に書く。

1. **残った誤読と詰まり**：読み手への影響が大きい順に、直せなかった理由と、直すために必要な判断を添える
2. **直したもの**：誤読や詰まりのどれに対応したかを添える
3. **挙動が変わる変更**：呼び出し側に必要な修正
4. **見つけたが設計改善の範囲外としたもの**：不具合や仕様の曖昧さ

読み手テストを省略した場合は、そのことと理由も書く。

## 適用しない判断

次の場合は何も変えないのが正しい。

- 読み手が誤読も詰まりもしていない。原則に照らして気になる箇所があっても、読み手に影響が無いなら直さない
- 数行で完結する単純な関数（`isWeekend` のようなもの）。定数化・設定化・クラス化しても読み手の負担が増えるだけになる
- 概念がまだ固まっていない。境界を早く引くと、誤った境界を跨ぐコストを払い続ける

迷ったら、名前を付けるだけで止める。型やモジュールを作らなくても、条件式や数値に名前を付けるだけで詰まりが消えることは多い。

## 実現手段はプロジェクトの規約に従う

網羅的な分岐、境界での型変換、名目的な型、依存の注入といった道具は、言語とライブラリで変わる。プロジェクトのコード規約に定めがあればそれに従い、無ければ既存コードで多数派の手段に合わせる。
