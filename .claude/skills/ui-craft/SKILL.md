# UI Craft

AI がゼロから UI を作ると、訓練データで最も多いパターンに寄って「どこかで見た画面」になる。そのうえ、描画結果を見ずにコードだけで完了とするため、崩れや冗長さが残る。

このスキルは 2 つの手段でこれを防ぐ。1 つは、既存のデザインシステムと参照実装を出発点にして、判断の余地を減らすこと。もう 1 つは、実際に描画した画面を見て直すループを、完了の条件にすること。

## 判断の優先順位

規則どうしがぶつかったら、上にあるものを優先する。

1. **プロジェクトの既存デザインシステムと既存コンポーネント**：利用者は既存の画面との一貫性で操作を学ぶため、単体で見て良い見た目より、隣の画面と揃っていることを優先する
2. **ユーザーが示した参照・要件**
3. **このスキルの原則**（下の「中心の原則」）
4. **`references/anti-patterns.md` の既定値**：既存の基準が無いときだけ使う出発点で、既存の値を上書きする根拠にはしない

## 中心の原則

- **中身から組む**：実際に入るデータと文言を先に決めてから配置する。ダミーの短い文言で組んだ画面は、本物の長さが入った瞬間に崩れる
- **レイアウトに説明させる**：意味は位置・グルーピング・順序・大きさで伝える。文字のラベルや説明文は、消すと意味を取り違えるものだけ残す（詳細は `references/anti-patterns.md` の「ラベル・説明文」）
- **強調は 1 画面に 1 か所**：すべてを目立たせると、どれも目立たない。主操作と最重要の情報を決め、それ以外は抑える
- **装飾は役割があるときだけ**：影・グラデーション・アニメーションは、階層や状態の変化を伝えるために使う。「寂しいから足す」装飾が AI 感の主な出どころになる
- **描画して確かめるまで完了にしない**：コードの上では正しく見えても、画面では詰まり・はみ出し・揃いのずれが起きる

## 作業の流れ

### 1. 理解する

- 何を作るか（部品 / 画面 / 画面の一部）と、使う人がその画面で達成したいこと
- 既存のデザイントークン（色・余白・角丸・文字サイズの変数）、既存コンポーネント、近い既存画面。まずこれを探し、あれば従う
- 技術スタック（フレームワーク、CSS の書き方）

### 2. 中身を決める

- 表示する項目を、利用者にとっての重要度順に並べる。並べられないなら、画面の目的がまだ曖昧なので 1 に戻る
- 実データに近いサンプルを用意する。最長の名前、0 件、大量件数、エラー時の文言を含める
- 各項目について、文字で書くか、配置や形で伝えるかを決める

### 3. 参照を選ぶ

ゼロから書かない。次の順で出発点を探す。

1. プロジェクト内の既存コンポーネントと近い画面
2. プロジェクトが使っている UI ライブラリの該当コンポーネント
3. `references/component-libraries.md` のカタログ

参照はそのまま貼らず、手順 1 で見つけたトークンと既存画面の書き方に合わせる。ライブラリのドキュメントは、ドキュメント取得用の MCP が使える環境ならそれで最新版を読む。

### 4. 実装する

- 値はデザイントークンから取る。新しい値が必要なら、その場に直書きせずトークンとして定義する
- hover・focus・active・disabled・loading・empty・error の状態を、最初から実装に含める。後から足すと、状態ごとに見た目がばらつく
- 迷ったら `references/anti-patterns.md` の該当カテゴリを読む

### 5. 仕上げる（描画 → 検査 → 修正のループ）

品質を最も左右する工程。1 回で終わらせず、検査で直すものが無くなるまで回す。

1. **描画する**：開発サーバーやコンポーネントのプレビューで実際に表示する。画素で描く UI はスクリーンショットを撮り、文字セルで描く UI（ターミナル・TUI）はプロジェクトが用意する方法で描画結果をテキストとして取り出す
2. **組み合わせを揃える**：狭い幅（375px 前後）と広い幅（1280px 以上）、ライト / ダーク（対応していれば）、手順 2 で用意した極端なデータ、各状態。1 枚だけ見て判断しない
3. **検査する**：`references/finishing.md` の検査を順に当てる。とくに次の 3 つは毎回行う
   - **目を細める検査**：画面をぼかして見たとき、最初に目に入るものが最重要の要素か
   - **引き算の検査**：要素・ラベル・線・影を 1 つずつ消したと想定し、失うものが無いものは消す
   - **揃いの検査**：左端・ベースライン・余白の段階が揃っているか。ずれは数 px でも「雑」に見える
4. **直して、1 に戻る**
5. **別の目で見る**：自分の検査で直すものが無くなったら、実装の意図を知らない読み手（サブエージェントなど）にスクリーンショットだけを渡し、「最初に何が目に入るか」「何をする画面に見えるか」「迷う箇所はどこか」を答えさせる。意図と食い違えば直す

変更前の画面があるなら、変更前と変更後を同じ条件で並べて比べ、良くなったことを確かめる。

## 完了の条件

- 手順 5 の組み合わせすべてで、崩れ・はみ出し・重なりが無い
- `references/finishing.md` の検査で、直すものが残っていない
- 別の目による確認で、画面の目的と最重要の要素が意図どおりに読まれた
- 文字のコントラスト比が 4.5:1 以上（大きな文字は 3:1 以上）で、キーボードだけで操作でき、フォーカスが見える
