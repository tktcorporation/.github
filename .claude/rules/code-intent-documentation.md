# コードコメントのルール

## 原則: Evergreen Comments（時間が経っても腐らないコメント）

コードに残すコメントは **Evergreen comments** / **Timeless documentation** / **Intent-only comments** と呼ばれる考え方に従う。骨子は次の 2 つ:

- コードに書けなかった情報だけを補う（実装で表現できることはコメントで重複させない）
- 履歴ではなく今の意図を書く（時間が経つと腐る情報はコードに混ぜない）

### 参考プラクティス

- Martin Fowler: "Good comments express intent at the level you cannot express in code"
- John Ousterhout "A Philosophy of Software Design": コメントは「コードに書けなかった情報」だけを補う
- Google C++ Style Guide: 実装コメントはコードの現在の振る舞いを説明するもので、変更履歴を書く場所ではない

### 判断基準

> 迷ったら「履歴を知らない新しいメンバーが読んだときに意味が通るか？」で判断する。通らなければ履歴情報なので削る。

この基準を通った「現在こうなっている WHY」だけを残す。WHAT（何をしているか）はコード自体が語るので書かない。

## 書くもの: 現在の WHY

コードを初見で理解するために必要な「なぜ今こうなっているか」を残す。

- ビジネス上の制約（例: 規約で〇〇できない）
- 設計判断の意図（例: 同期負荷を避けるため非同期化）
- 気づきにくい副作用・前提
- 削除判断の材料（例: 〜が不要になれば削除可能）

> ⚠️ 設計判断の意図を書くときも、**変更前の状態を前提にしない**。「なぜ今これを追加／変更したか」を「以前は〜だった」と引き合いに出して説明すると、変更前を知らない読者にはノイズになり、状態が進むと陳腐化する。追加・変更の「理由」は変更時点の文脈なので PR／コミットに書く。コードに残すのは、現在の状態だけで意味が通る「今の制約・意図」だけにする。

### 該当箇所

- **公開関数** (`export`): JSDoc で目的・背景・使用箇所
- **非自明なロジック**: 「なぜこの方法か」「なぜこの順序か」
- **ワークアラウンド**: 理由と、いつ不要になるか
- **型・インターフェース**: 何を表現しているか / ライフサイクル
- **定数**: マジックナンバーの由来
- **防御的デフォルト値・非自明な初期化**: なぜここでこの値か

## 書かないもの

### 1. WHAT（コードが既に語ること）

実装を読めば分かることをコメントで重複させない。

- 自明なゲッター/セッター
- フレームワークの定型パターン
- 型名やパラメータ名から明らかなこと

### 2. 歴史・経緯（時間が経つと腐るもの）

| 書かないもの | 例 |
|--------------|----|
| 過去との対比 | 「元は X だったが Y に変えた」「従来は〜」「legacy 〜」「以前の実装と同じルール」 |
| 追加・変更の理由（変更前を前提に説明） | 「最低を 400 にしているのは、最低が 500 だと〜なため」「X を追加したので〜」（"500 が最低だった" という過去を前提にしており、選択肢が増えると陳腐化。理由は PR／コミットへ） |
| 変更履歴 | 「2024 年 3 月に導入」「〇〇対応で追加」 |
| 個人名・担当者名 | 「〇〇さんが書いた」「△△担当のロジック」 |
| コミット SHA / PR 番号への参照 | 「9b4909a と同じ方式」「PR #1234 で導入」 |

これらは **git log / PR description / 設計ドキュメント** の仕事。コードコメントに混ぜると、前の状態を知らない読者には「そんなん知らんがな」なノイズになり、履歴が進むと陳腐化する。

## 初見の読者に向けて書く（可読性）

コメント/docstring は、このコードを今日初めて読む人が文脈なしで理解できる粒度・順序で書く。WHY を書くこと（上記）とは別軸で、「書いた WHY が初見の読者に届く形になっているか」を扱う。自分が把握済みの文脈・専門用語を前提にすると、語彙密度が高くなり読み手が素通りする。

### 書き方の指針

- **冒頭 1 行で「このコメントは何のためか」を平易な日本語で書く**。技術用語は必要な分だけ後ろに足す。
- **「何をする → なぜそうする → どう動く」の順で組む**。逆順だと、結論が届く前に専門用語が並ぶ。
- **関数の docstring は「この関数が何をやっているか」を 1 文書いてから詳細に入る**。既知文脈を仮定しない。
- **抽象語を単体で使わない**。「規約で」「設計上の理由で」では何も伝わらない。事象で説明する。
- **長文 1 つより、短い文を 3〜4 文重ねる**。読み下しやすさが上がる。

### 抽象語 → 事象（例）

| 避ける（抽象語の単体使用） | 書き換える（具体的な事象） |
|---|---|
| 「設計上の理由でここは JOIN しない」 | 「ここで JOIN を足すと走査行数が増えてクエリが遅くなるため、別クエリに分ける」 |
| 「規約で N 件までに制限」 | 「1 リクエストで N 件を超えると外部 API がエラーを返すため N 件で打ち切る」 |
| 「パフォーマンス対策」 | 「同じ ID で何度も問い合わせると同期負荷が上がるため、取得結果をここでキャッシュする」 |

### セルフチェック

> このコメントだけを、前後のコードと社内文脈を知らない人が読んで意味が通るか？ 通らなければ、専門用語を事象に開くか、1 文目に「何のためか」を足す。

技術現象を説明するときは、機構名（covering index・nested loop 等）と実際の発生条件を取り違えないこと。名前だけ正しくても条件がずれると初見の読者を誤解させる。
