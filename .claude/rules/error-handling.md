# エラーハンドリングの設計

エラーを「値として返すもの」と「投げるもの」に分け、返す側は呼び出し元が網羅的に扱える型で表現する。**値か例外か**と、**運用上の異常として監視するか**は別の判断である。`robustness.md` が「不正な状態を作れない設計」を扱い、本ルールは「起きた失敗をどう表現し、どこまで運ぶか」を扱う。

## 原則 1: 予期されたエラーは値で返し、予期しないエラーは投げる

| 種別             | 定義                                   | 扱い                     | 例                                                       |
| ---------------- | -------------------------------------- | ------------------------ | -------------------------------------------------------- |
| 予期されたエラー | 正常系の一部として起こりうる分岐       | 戻り値の型に含めて返す   | 対象が存在しない、入力が不正、外部サービスのタイムアウト |
| 予期しないエラー | 起きたらプログラムかインフラ側の不具合 | 投げて上位へ届ける       | 接続断、メモリ不足、到達不能なはずの分岐                 |

境界は **呼び出し元がその場で意味のある対処を選べるか**。選べるなら値で返す。選べないなら投げる。タイムアウトを値で返して代替応答に進む場合でも、予期しない内部・依存先障害なら下記の監視判定を別に行う。

## 原則 2: エラー型は網羅可能に定義する

失敗理由を 1 つの汎用型に潰すと、呼び出し元は分岐を書けず、失敗理由が増えても気づけない。判別可能な union で表現し、呼び出し元が網羅的に扱えるようにする。

```typescript
// ❌ 何が起きたか呼び出し元が判別できない
function getData(): Result<Data, Error>;

// ✅ 理由ごとに分岐でき、増えたときは型が教える
type GetDataError =
  { type: 'NOT_FOUND'; id: string } | { type: 'VALIDATION_ERROR'; message: string };
function getData(): Result<Data, GetDataError>;
```

## 原則 3: 捕捉した例外は分類してから返す

外部から飛んできた例外をそのまま自分のエラー型に載せると、予期しないエラーまで「予期されたエラー」に化けて監視から消える。捕捉したら分類し、自分が意味を与えられるものだけを値にして、残りは再スローする。代替応答のために内部障害を値へ変換するなら、利用者への応答とは独立に、監視する責任境界を決める。

## 原則 4: 原因を捨てない

新しいエラーで包むときは元のエラーを cause として繋ぐ。メッセージだけを文字列連結して投げるとスタックトレースが切れ、発生源を追えなくなる。これは内部の原因追跡用であり、生の例外や cause を外部の監視イベントへそのまま送る許可ではない。

## 原則 5: 握りつぶさない

ログ出力だけして処理を続けるのは、失敗を隠して後続を壊す。呼び出し元へ返すか、投げて上位へ届けるかを決め、内部障害の監視要否は別に判定する。

## 運用上の異常を監視する

利用者が選べる正常な拒否（未契約、通常の利用枠切れ、不正入力、通常の権限拒否、明示的な中止、重複操作）は、個別の障害イベントを送らない。運用の集計が必要なら、個人情報を含まない集計値を別に設計する。欠損データは一律に分類せず、その操作で正常に起こる不在か、守るべき不変条件の破れかを判定する。

DB の読み取り・接続失敗、依存先の認証設定不備・想定外の制限・5xx・タイムアウト・不正な応答、不変条件違反、到達不能な分岐は、代替応答や結果型で処理しても内部障害として監視する。外部依存のタイムアウトが通常の制御分岐でも、運用上の異常かどうかは依存先との契約と期待頻度で判定する。

監視を実装する際は次を満たす。

1. **責任境界**: 1 つの要求・障害に対して、入口・依存先・代替応答のどこが最終イベントを送るか決める。下位と上位の二重送信、SDK の自動捕捉との重複を確認する。各リトライ失敗を個別送信せず、成功したリトライは必要なら劣化の集計、最終的に失敗した場合は 1 件の障害イベントとする。タイムアウト後の遅延応答も二重送信しない。
2. **固定分類と安全な内容**: イベント名・fingerprint・reason・stage はコードで定義した有限の分類値だけを使う。要求本文、利用者や対象の ID、任意 URL、トークン、決済情報、生の例外・stack・cause をイベントへ載せない。外部送信直前の最終イベント全体（request、user、breadcrumb、scope、attachment を含む）を検査・除去し、SDK の既定収集も確認する。内部で cause を保持することと外部送信は分ける。
3. **通知量と可用性**: 理由ごとの抑制・サンプリングを設計し、並列要求を一括で隠すグローバルな抑制を避ける。監視先の失敗で利用者向けの代替応答を壊さない。監視先が未設定のローカル・テスト環境では外部送信を 0 件にし、その環境では障害が外部から**未観測**であることを検証・報告する。

受入例: 通常の入力拒否と枠切れは障害イベント 0 件。内部 DB 障害を代替応答に変換しても最終イベント 1 件。リトライ・タイムアウト後の遅延応答で同じ障害を再送しない。機密を模した目印は最終イベントに残らず、監視先の失敗と未設定時にも代替応答は維持される。ルールの参照や静的検査だけでは実コードの送信内容・件数を検証済みとは扱わず、実装時に送信直前のイベントと分岐をテストする。

## レイヤーごとの責務

| レイヤー                                                        | 責務                                                         |
| --------------------------------------------------------------- | ------------------------------------------------------------ |
| 外部境界（リクエストハンドラ・外部 API クライアント・永続化層） | 外部の例外・エラーレスポンスを自分のエラー型へ分類する       |
| ドメイン / サービス                                             | 予期されたエラーを型に載せて返す。予期しないものは通過させる |
| 利用者に面する入口                                              | エラー型を網羅的に扱い、利用者向けの表現へ変換する           |

## 禁止パターン

| パターン                                              | 問題                                                   |
| ----------------------------------------------------- | ------------------------------------------------------ |
| メッセージだけを連結して新しいエラーを投げる          | スタックトレースが切れ、発生源を追えない。cause で繋ぐ |
| 捕捉してログ出力だけで続行                            | 失敗が隠れ、監視に届かない                             |
| エラー型を汎用型（`Error` / `any` / `unknown`）にする | 呼び出し元が分岐を書けない                             |
| 捕捉した例外を分類せずそのまま自分のエラーにする      | 予期しないエラーが予期されたエラーに化ける             |

## 生の try-catch を書いてよいケース

原則として、失敗しうる処理は結果型を返す仕組みで包む。生の try-catch を書くのは次のときだけ。

1. `finally` でリソースを解放する必要がある（獲得と解放を対で扱う仕組みを先に検討する）
2. 捕捉した例外を分類し、予期しないものを再スローする

### try-catch ガードは呼び出し箇所ごとに書く

例外を握るだけの薄い処理を、呼び出し元の操作名を文字列で受け取る共通ヘルパー（例: `guard('methodName', () => sdk.methodName(...))`）に切り出すと、渡した文字列と実際に呼ぶメソッドが一致しているかを型で確かめられなくなる。呼び出しもコールバックで一段挟まり、直線的に読めなくなる。

握る対象が1関数あたり1呼び出しで、各呼び出しが短いなら、その場に try-catch を直接書く方が短く、型で守られる範囲も広い。同型の try-catch が複数並ぶと自動レビューは共通化を推してくるが、重複の解消より直線的に読めることを優先してよい。

## 実現パターンの例

言語・ライブラリによって手段は変わるが、代表的な組み合わせは次のとおり。

| 原則                       | パターンの例                                                                                                                       |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 予期されたエラーを値で返す | Result / Either 型で返す（例: TypeScript + Effect の `Effect<T, E>`、Rust の `Result<T, E>`、関数型ライブラリの `Either`）         |
| 捕捉した例外の分類         | 網羅的なパターンマッチで分類し、未知のケースは再スローする（例: ts-pattern の `match().otherwise()`、Rust の `match`）             |
| 原則の自動強制             | 静的解析ルールで違反パターン（cause 無しの再スロー・握りつぶし・曖昧なエラー型など）を検知する（例: ast-grep, ESLint custom rule） |
